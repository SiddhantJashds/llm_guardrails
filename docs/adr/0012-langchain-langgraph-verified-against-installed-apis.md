# 0012. LangChain/LangGraph integrations verified against installed APIs

Status: Accepted
Date: 2026-10-05

## Context

`governance_sdk`'s LangChain/LangGraph integration code was written against assumed framework APIs and explicitly flagged as unverified: `wrap_graph_nodes`'s own docstring said "verify the exact attribute path against the installed langgraph version -- this sketches the intent, not a tested API surface"; `GovernanceCallbackHandler.on_llm_end` was a bare TODO; `examples/langchain_single_agent.py` and `examples/langgraph_multi_agent.py` referenced `langchain.agents.AgentExecutor`/`create_tool_calling_agent` as TODOs, neither ever run. This is SWE#1 Day1 #6 / Day2 #7.

Actually installing the real libraries (`langchain==1.4.3`, `langchain-core==1.6.6`, `langgraph==1.2.12`) and running real agents/graphs against the real `governance_api` (in-process via `fastapi.testclient.TestClient`, no server/socket/API-key needed -- `httpx.Client(transport=httpx.ASGITransport(...))` was tried first and doesn't work: that transport is async-only) surfaced four real, concrete problems, not just "needs updating for a newer version":

1. **`langchain.agents.AgentExecutor` / `create_tool_calling_agent` no longer exist.** LangChain 1.x replaced them with `langchain.agents.create_agent`, which returns a compiled LangGraph graph internally, and takes `callbacks` at invoke time via `config={"callbacks": [...]}`, not at construction.

2. **`StateGraph.nodes[name].runnable` is a `RunnableCallable`, not directly callable.** Confirmed: calling it raises `TypeError: 'RunnableCallable' object is not callable`; it only exposes `.invoke()`/`.ainvoke()`. `wrap_graph_nodes`'s original code assigned a plain wrapped function straight onto `.runnable`, which would have broken the moment anyone actually compiled and ran the graph it was "wrapping."

3. **Critical: `BaseCallbackHandler` exceptions are swallowed by default.** `langchain_core.callbacks.manager.handle_event` catches any exception a handler raises and only re-raises it if `handler.raise_error` is `True` (default: `False`) -- otherwise it logs a warning and the run *continues as if nothing happened*. Confirmed by direct test: a `PermissionError` raised in `on_tool_start` for a degraded agent was logged, and **the tool executed anyway**. This made `docs/INTEGRATION_CONTRACT.md`'s documented promise -- "a denial raises `PermissionError` before the tool executes" -- false for the LangChain single-agent integration path as shipped. This is the most serious finding here: a governance mechanism that looks like it's enforcing something while actually only logging it is worse than no mechanism at all, because it reads as working in casual testing.

4. **`governed_node`'s `str(output)` re-penalizes every downstream node for an upstream leak it didn't cause.** LangGraph nodes conventionally return a partial state update that gets merged into cumulative state (`{**state, "my_field": ...}`, the idiom this repo's own examples already used) -- so `output` almost always still contains every key a prior node set. Confirmed with a real 3-node graph: the 3rd node's own output had no PHI at all, yet it still took the same `-20` penalty the 2nd node (which actually leaked it) already took, purely for carrying the leaked value forward in state. The original code's own comment already flagged this generally (`# TODO: extract the actual text field(s) from output`) without implementing a fix.

## Decision

1. `examples/langchain_single_agent.py` rewritten against `create_agent`, using a small deterministic `ScriptedChatModel` (implements `bind_tools` as a no-op, returns pre-scripted messages) instead of a real provider -- no API key or network call needed to verify the wiring, consistent with [0004](0004-deterministic-compliance-no-self-attestation.md)'s spirit of not needing an LLM call to prove the governance layer itself works.
2. `wrap_graph_nodes` fixed: mutates `spec.runnable.func` in place (the real attribute holding the original function) rather than replacing `.runnable` wholesale -- confirmed, by compiling and invoking a real graph, that this mutation propagates correctly through the actual executor, not just a direct `.invoke()` call on the node spec.
3. **`GovernanceCallbackHandler.raise_error = True`**, set as a class attribute with an explicit comment explaining why it is not optional. `on_llm_end` now runs a real outbound compliance check and raises on `block` (mirroring `on_tool_start`'s denial behavior) -- with a documented limitation: unlike the proxy, a callback can't reliably rewrite the text the agent continues with, so `redact`/`hash` verdicts are recorded and penalized but don't change what the agent sees next. Use the proxy path for guaranteed redaction of the end-user-facing text.
4. `governed_node` now diffs `output` against the input `state` (`_new_or_changed_text`) and only checks/penalizes what THIS node actually added or changed; a node that changes nothing skips the handoff-check call entirely (nothing to evaluate, no receipt written for a no-op).
5. `GovernanceClient` gained an optional `client: Optional[httpx.Client]` constructor param (default `None`, zero behavior change for real usage) so tests can inject a `TestClient` instead of needing a real running server.
6. `governance_sdk/tests/` (new): the above is pinned as repeatable pytest integration tests, not just something verified once by hand -- including an explicit regression test that a denied tool call's underlying function genuinely does not execute (not just "no exception reached the test"), which is exactly the class of bug #3 above would otherwise hide.

## Consequences

- SWE#1 Day1 #6 and Day2 #7 are now genuinely done, not "written but unverified" -- both integration points run a real agent/graph against the real governance_api, in CI, with no external dependency.
- #3 is the one worth flagging loudest to the rest of the team: if anyone else is holding a `BaseCallbackHandler` subclass anywhere in this codebase for an enforcement purpose (not just logging/observability), it needs the same `raise_error = True`, or it's not actually enforcing anything.
- `governance_sdk/pyproject.toml` deliberately still lists only `httpx` as a hard dependency (LangChain/LangGraph are integration-only, per `langchain_callback.py`'s own docstring) -- the new test dependencies went into `requirements-dev.txt`, not the SDK's own package metadata.
- `data_pipeline/__init__.py` and `governance_sdk/__init__.py` (new, both empty) were needed alongside this to disambiguate `data_pipeline/tests` and `governance_sdk/tests` from `governance_api/tests` under pytest's import machinery -- all three previously-separate `tests/` directories were colliding on the same bare `tests` module name the moment more than one was collected in the same run (mirrors the existing `detectors/__init__.py` precedent).
- LangChain 1.x's `create_agent` returning a compiled LangGraph graph internally is a real convergence worth knowing about -- the two documented "integration points" (option 2 and option 3 in `docs/INTEGRATION_CONTRACT.md`) are more architecturally similar now than when that document was written, though this ADR doesn't restructure that document's framing, just its two examples' actual code.
